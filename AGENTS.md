# Collaboration

- Validate features practically in the application first. Do not routinely add automated tests; match further checks to the user's needs.
- Respect existing workspace changes and user data.
- Keep routine checks local and proportionate; do not introduce push/PR test workflows. The user-authorized exception is the release installer workflow: build macOS/Windows packages without trusted publisher certificates when a release is published, plus an explicit manual build for validation. Keep that exception focused on packaging and release assets.
- Maintain repository documentation in English. Keep relative links and heading anchors valid, link new guides from the [documentation index](docs/README.md), and distinguish implemented features from design targets. Keep actual code identifiers and interface labels intact when citing them.

# Settings

- Follow the [settings design](docs/settings-design.md): category navigation, global search, and compact expandable groups with state summaries.
- Make settings discoverable through common synonyms and usable in narrow windows.
- Support keyboard operation and understandable labels. Clearly communicate saves, immediately applied changes, and errors.
- Group mail settings by account. Allow prefilled editing of general/IMAP and SMTP configuration, check and save reception and sending separately, and preserve account IDs, drafts, and other unsaved account edits.
- Preserve unsaved inputs when switching categories, searching, or expanding and collapsing groups. Integrate new settings into the existing structure and search.

# Product principles

- OpenVibeDesk is a fully integrated AI workspace. The OVD Assistant is an equal entry point to every implemented domain feature: mail, drafts, files, windows, chats, and settings. Implement this integration with each change, rather than deferring it as a future possibility.
- The interface and assistant use the same domain services through shared, typed, validated capabilities. Do not create a deliberately reduced parallel feature set for the assistant. A new or changed interface action is fully integrated only when the assistant can reach the appropriate capability under the existing permissions.
- Interpret tool results and activity status from the same actual outcome. Empty error fields are not failures; explicit errors, cancellation, and uncertain outcomes must not be reported as success. Never automatically resend mail after server acceptance or an uncertain sending result.
- Answer reformulation uses the dedicated host text-only path and saved bounded evidence. Never route it through the normal agent loop, reread sources or execute tools, including under **Without confirmations**. Missing or unfinished evidence is a visible limitation, never a reason to replay an old request. Editing and sending a request is a separate new execution; durable action continuation/reconciliation remains distinct.
- Agent continuation uses the acknowledged operation journal and the original root/action identities. Persist intent before dispatch and its actual outcome afterwards. Reuse completed results; never retry an uncertain mutation without an authoritative, separate status check. `operations.retry` selects exact host-held arguments inside an explicit continuation; it must not create a new task or bypass current permissions, code/schema approval or resource-version checks. New unplanned mutations require a separate user request. Never automatically resume after restart, deduplicate unrelated requests by text, or evict accepted/unknown guards to make space. Storage failures stop execution visibly. Read policy means audited absence of business-data mutation; a harmless search-results view may still be presented.
- Describe capabilities, prerequisites, required resources, and approvals in the offered capability catalog. The assistant's claims must follow that catalog and execution results. Fix a missing integration as a specific gap; do not claim blanket inability or report an unperformed action as completed.
- The Assistant is the required `ovd-assistant` module; domain features such as Mail belong in their own modules. Keep new domain logic, views, settings, and tools in the responsible module. Register through `module.json` and the module host, not additional special cases in chat.
- The optional file manager lives in [modules/ovd-files](modules/ovd-files/). Both the interface and assistant can access local paths within OS permissions; do not add a Documents-only restriction, path allowlist, or mandatory folder picker. Documents is a starting point, not an access boundary. File references use the generic module/type/resource-ID contract. Only the responsible backend resolves IDs and content; supplied text is not trusted reference content. Label unsupported formats honestly as metadata-only.
- MCP lives in the optional [modules/ovd-mcp](modules/ovd-mcp/README.md) module. Offer dynamic server sources through the generic provider contract; do not add MCP-specific branches or complete server catalogs to chat. Only saved servers and explicitly approved current tools may execute. The assistant may prepare configuration and tool permissions in a form, but may not save them or expand access itself. Keep secrets in the OS credential store. After a timeout or disconnect with possible external changes, do not automatically retry; reject changed or revoked offers before execution.
- Take agent execution limits exclusively from the centrally validated configuration; do not add hidden round or call limits. When a limit is reached, show a clear status, counters, and retained results. Changing settings must not automatically repeat running or completed actions.
- Keep model context small: initially expose only short module descriptions and the two discovery tools. The assistant finds modules with `find_modules`, loads the required functions with `get_module_tools`, then invokes them. Do not send full module or tool catalogs on every request or store schemas in durable chat history. New modules must work through this flow without changing the system prompt.
- Include current system time, local date, IANA timezone, and locale as a small host context in each request. Resolve relative calendar periods centrally with daylight-saving rules; do not infer day boundaries from old messages. Counts and lists share validated domain filters and state scope, observation time, and completeness. Do not infer a complete total from a loaded subset; `countExact=false` denotes a lower bound. Use bounded, typed calculation operations rather than arbitrary code evaluation.
- Module authors are responsible for complete assistant control through the same validated functions. Descriptions, search terms, bounded results, cancellation behavior, and required confirmations belong in the [module contract](CONTRIBUTING.md#building-modules).
- Execute third-party modules only after explicit local approval of their file fingerprint. Changed code requires new approval. The separate backend process isolates crashes but is not an OS sandbox; do not describe declared permissions as enforced OS boundaries.
- The actual mail interface follows the [mail design](docs/mail-design.md), and settings follow the [settings design](docs/settings-design.md). Both are lasting product requirements and include future development stages.
- Focus on real accounts and content. Do not add a separate visible demo or sample mode as a substitute for the actual interface.
- Keep the interface consistent: compact title bars, lean views, understandable labels, accessible icons, and usable narrow-window layouts.
- Visual identity follows the supplied CI package, [brand guide](docs/brand.md), 20 unchanged `ovd-*.svg` master files under [assets/brand](assets/brand/), and [design tokens](assets/brand/source/tokens.json). The symbol has O/D with pupils, an upper navy V, and a separate violet triangle underneath; do not remove or redraw them. Use the supplied wordmark paths and local Manrope font with its OFL license. Do not add effects; respect clear space and minimum sizes. Violet on Lavender has only 4.21:1 contrast: use Navy or Ink for normal text on that background.

# Preserve existing workflows

- Keep chat compact. Place message actions outside the user bubble, reachable on hover or keyboard focus. Hidden actions must not enlarge bubbles or cause layout shifts. Keep them visible on devices without hover.
- Keep generic chat text, reference drop hints, and their icons independent of module type. Use concrete labels such as email or chat only for known references, including selection and removal. A generic drop target must not assume a default module type.
- Optional modules supply their own resource titles and descriptions through reference metadata. Keep shared chat copy and host errors module-neutral; describe generic roles such as context or instruction without hardcoding an optional feature's name. Preserve the visible instruction role and request-scoped activation rules.
- Render chat as CommonMark with GFM extensions. Preserve real keyboard-accessible links; validate external destinations in the main process and open them through the default application. Copying, editing, references, and branches retain the original Markdown source. Tables and code must not widen narrow chat windows.
- Let the composer grow and shrink with its content. Respect a manually chosen reading position during streaming and provide a visible route to the newest message. Summarize tool activity compactly and expose failures in the summary.
- Carry existing functions through interface changes, including drag and drop between native windows, mail/chat references, chat navigation, drafts, and attachments. Do not silently remove these connections.
- Handle mail references end to end: dragging from the actual mail view, visible selection in chat, removal before sending, actual mail context at the provider, and preservation in saved history and chat branches.
- Drag payloads contain only resource identity. The main process resolves and validates it; arbitrary supplied mail text is not trusted. Mail content remains untrusted data.
- References give the assistant a stable resource ID and a bounded excerpt explicitly marked as a snapshot. Retrieve complete or current content through the responsible module's reading function with continuation; even long individual texts must remain reachable. Opening a window does not replace reading content. Do not recursively resolve nested references without a request.
- With Workspace tools enabled, the assistant may autonomously discover, search, list, count and read configured domain resources needed for the user's task, and navigate their views. Do not require per-mail selection, result grants, a separate general-mail switch or extra read-confirmation dialogs, including in the default confirmation mode. References select useful context; they are not read-permission tokens. Keep resource identity and task scope explicit. Users configure their own AI provider; do not add routine provider-transfer notices to chat, settings or permission dialogs.
- The assistant can initiate the prepared flow for sending, destructive changes, and protected settings. By default, final execution uses the same understandable, visible user approval as the interface; scope and effects must be reviewable first. Under AI → Workspace access, the user can explicitly enable **Without confirmations** (currently **Ohne Abfragen**). The host then performs requested assistant actions without individual confirmation dialogs, while preserving access rights, secret protection, and separate approval of new or changed third-party modules. This mode is off by default; the assistant may only prepare it in the form, never enable it itself. Do not categorically exclude these functions from assistant access.
- Keep credentials and secrets in secure storage. The assistant can open the relevant setup/editing dialog and edit allowed metadata; passwords and keys must not appear in model context or tool results. Autonomous domain reads do not grant secret access, approve module code or bypass configured MCP tool permissions. Local file access follows the shared Files module contract and OS permissions.

# Completing a change

- Before finishing an application change, practically exercise the affected user workflow through the interface and assistant across the relevant windows and boundaries. A successful build, visible button, or new tool schema alone does not validate that workflow.
- For new functions, compare interface actions with assistant capabilities. Carry a concrete request such as “Open a new email to this message's sender” through to the correct draft and verify visible fields, including required permission and approval steps.
- For mail and chat changes, check the transition from actual mail data to chat references and back to the relevant view. For persisted references, also check restoration and branching.
- Use synthetic data or a designated test mailbox. Never send real mail or change existing mailbox content to test a feature.
- Check TypeScript and the build as appropriate to the change. Do not routinely add automated tests; necessary focused checks may support the user workflow. For documentation-only changes, check links, examples, factual accuracy, and generated document rendering as applicable.
